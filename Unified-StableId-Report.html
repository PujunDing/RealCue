4数据链路：两条入口，同一套决策

两条入口共用同一个 FaceRepository （FeatureHub 是进程级单例，全程留在同一个 SDK 线程上，不跨线程切 native 生命周期）。 若库打不开，视频页会自动降级为原来的 ID n，不会把相机页面弄崩。

6顺手修掉的两个真问题

① 编译阻断：上一轮被总结请求打断时， FaceDetectionActivity.updateSelectionStatus() 已经引用了 R.string.detection_face_selected_stable，但中英文 strings.xml 里都还没定义 —— 这个状态下 compileDebugJavaWithJavac 会直接失败。 已补齐，并用 aapt2 dump resources 确认中英实际值真的进了 APK。
② 改 Session 参数后标签退化： rebuildSession() 原来仍调 detectWithLandmarks()、不重算 imageFaceLabels、不调 setFaceLabels()，用户输入 px / 最大脸数一改，图片框就退回 1/2/3 或沿用错位的旧标签。 已改为稳定模式下走 detectWithLandmarksAndFeatures() + resolveStableLabels() 回传 labels，并补上旧 crops 回收。
编译闸门实测：BUILD SUCCESSFUL in 33s， 资源合并与 Java 编译都重新执行，不是 UP-TO-DATE 假通过。

这条 0.9849746 为什么重要

它不是「同一份特征跟自己比」得到的 1.0，而是同一个人换了一次成像条件 （JPEG 压缩 + 亮度变化）后重新提特征再查库得到的分数，且 gallery=1 证明没有因为重入而新建第二个身份。这正是你截图里「同一张脸却依次编号」的反面结果。

高出阈值约 0.505，但这只是同人稳定性； 异人分数分布仍然没测，不能据此说「已经很准」。

9诚实边界与真机怎么验

必须重新上传安装 APK。为回应「重新编译过没」的质疑， 本轮又做了一次 --rerun-tasks 强制全量重编译（65 / 65 tasks executed）， 最终交付包为 116,455,212 B · 2026-11-16 14:14:54。 比上一版 117,605,130 B 小 1,149,918 B，是重新打包的压缩差异； native libs / 两个模型 / kun.jpg / 9 dex / 资源已逐项核对齐全。 手机上那份旧包不会自动更新 —— 不重装的话你看到的仍会是 ID n。
  1. 把新的 app-debug.apk 重新传到 Xiaomi 14 Pro 并安装（覆盖安装即可，人物库数据按模型隔离保留）。
  2. 直接打开你原来那个「人脸跟踪」页，不用再找新卡片：切到「图像检测」，选一张人脸照片，框上应是 P001 / P002 而不是 1/2/3。
  3. 切到「视频跟踪」，露出脸拿到 P001；完全离开画面几秒再回来，应仍是 P001，不会变成 ID 2。
  4. 去「人脸管理」应能看到该记录显示为 P001，搜索框输入 P001 能搜到。

还没收口的边界

  • 阈值 T_match=0.48 / T_new=0.36 仍是 B0 占位值，两个真人样本未采集；B0 的 doNotUseForThreshold 警告依然成立。
  • 灰色区 FaceRepository.open() 把 FeatureHub 搜索阈值设为 SDK 推荐值，低分候选被提前过滤，生产线实际只有「高分命中 / 无候选」两种状态。
  • 视频页 稳定标签没有设备端直接断言：它依赖 CameraX 实时帧与 GL overlay，无法在 instrumented test 里直接实例化。其决策内核由 15 项 JVM 单测 + B3 三项设备端重入测试覆盖，recognition Session 分支由 SESSION_SWITCH 类比验证，但真机视频效果仍需你实机确认。
  • 样本 仍只有一张 kun.jpg；异人分数分布、多人同框、帧率、最终准确率都未测。
下一步优先级：① 重装 APK 做上面的 A/B/C 重入验证； ② 两个真人各 3~5 张跑 runtime/calibrate_threshold.py 拿到真实 T_match / T_new；③ 若要灰色区生效，让 FeatureHub 搜索阈值可配置。
